# ADR 0002：规划助手采用领域工作流而非通用 Agent

- 状态：已接受
- 日期：2026-11-03

## 背景

StuKit 需要使用用户自己的大模型 API，分析培养方案、竞赛和训练营资料，并维护长期学习
与生活规划。直接增加聊天框无法提供稳定的数据结构、证据引用、版本历史和跨模块边界；
引入拥有文件、命令和网络权限的通用 Agent 又会扩大安全面，并绑定某一家厂商的工具协议。

## 决策

规划助手采用 StuKit 自己维护的窄领域工作流：资料由用户主动导入，Application 按固定
阶段构建上下文、调用 Provider、验证结构化结果并生成规划版本。模型服务通过
`ILanguageModelService` 适配，API Key 通过 `ISecretStore` 保存。任何跨模块写操作都生成草稿并
等待用户确认。

首版不提供任意命令执行、后台自主循环、隐藏网络访问或自动报名等通用 Agent 权限。

## 结果

优点：

- 资料、规划和历史不依赖具体模型服务。
- 可对确定性规则进行自动化测试。
- 能展示来源、假设和置信度。
- API Key 和跨模块写操作具有明确安全边界。
- 后续可以逐个增加服务商，而不重写规划业务。

代价：

- 需要自行实现上下文构建、状态机、结构验证和版本管理。
- 首版能力少于成熟通用 Agent。
- 每种 Provider 仍需维护独立适配器和能力声明。

## 被拒绝的方案

1. 仅提供聊天框：无法形成可靠、可追踪的规划资产。
2. 直接依赖单一厂商 Agent SDK：短期功能较多，但数据和工具流程被厂商绑定。
3. 让导入文档驱动工具调用：存在提示词注入和越权修改风险。
