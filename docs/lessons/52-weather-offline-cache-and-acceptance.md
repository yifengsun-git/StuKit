# 第五十二课：天气离线缓存与模块验收

## 本课目标

让天气页面在应用重启和网络故障后仍能显示最近一次成功预报，并完成天气模块 MVP
验收。缓存只是离线兜底，界面会明确标出缓存状态和数据更新时间，不把旧数据伪装成
实时天气。

## 本课完成内容

### 1. 建立缓存端口

`IWeatherForecastCache` 位于 Application 层，只描述两个动作：按地点读取预报、保存
成功预报。`WeatherViewModel` 依赖这个抽象，不知道数据最终写入 JSON、SQLite 还是
移动端平台存储。

这条依赖边界给 Android 留下了替换实现的空间，也让 Presentation 测试可以使用内存
测试替身，不必真实操作文件。

### 2. 实现版本化 JSON 缓存

`JsonWeatherForecastCache` 位于 Infrastructure 层，保存地点、当前天气、逐日预报和
UTC 抓取时间。文件包含 `schemaVersion`，将来字段变化时可以识别旧格式。

写入使用 `QSaveFile`：内容先写入临时文件，完整成功后再原子替换目标文件，降低程序
中途退出造成半个 JSON 文件的风险。读取时会重新经过 `WeatherLocation` 和
`WeatherForecast` 的领域校验；损坏、版本不符或地点不匹配的缓存会被安全忽略。

缓存路径为应用数据目录下的 `weather-cache-v1.json`，不在 Git 仓库内，因此不会提交
到 GitHub。

### 3. 离线回退流程

启动并恢复上次城市后，ViewModel 先尝试读取缓存，再发起网络刷新：

```text
恢复城市 -> 有缓存则立即展示 -> 异步请求最新天气
                            -> 成功：保存并显示实时数据
                            -> 失败：保留缓存并显示错误提示
```

用户切换城市时会先清空旧城市预报，只加载与新城市精确匹配的缓存，避免地点和天气
错配。`usingCachedForecast` 属性让 QML 显示“正在显示上次缓存的数据”。

## 测试覆盖

- JSON 缓存完整写入与读取。
- 损坏 JSON 和地点不匹配时拒绝读取。
- 启动先恢复缓存，同时继续请求最新数据。
- 网络失败保留缓存；网络成功保存新数据并退出缓存状态。
- 原有天气 Presentation、QML 响应式和 Open-Meteo 解析测试继续通过。

## 你需要理解的重点

离线能力不是在页面里直接 `QFile` 读写，而是一个跨层协作：Domain 保证数据有效，
Application 定义端口，Infrastructure 负责 JSON，Presentation 决定何时加载和回退，
QML 只展示状态。这样每一层都只有一个清晰职责。

## 验收标准

- 第一次联网成功后生成缓存。
- 重启应用可先看到上次预报。
- 刷新失败不清空已有缓存。
- 缓存状态与更新时间清晰可见。
- Debug 构建、QML 静态检查及全部测试通过。
