# 第七十课：UI-5 验收基线与人工清单

## 本课目标

本课进入 UI-5，不再增加业务功能。目标是把“程序能够编译”提升为可重复的验收流程，
明确哪些结果已经由自动化证明，哪些必须在真实 Windows 窗口和 Android 手机上确认。

## 一、自动验收基线

当前代码已经通过以下检查：

- Qt 6.10.3、MSVC 2022 Debug 完整构建；
- 60/60 项 Qt Test，包括领域、用例、SQLite、组合根和 QML 响应式测试；
- Windows 应用启动 5 秒，无标准输出或错误输出；
- Android arm64-v8a 原生代码、QML 缓存和 Gradle Debug APK 打包；
- `git diff --check`，没有尾随空格或补丁格式错误。

QML 集成测试已经覆盖 360、640、960、1280 和 1440 px 等关键宽度，以及 360 × 480
长表单约束、底部操作区、筛选折叠和最大内容宽度。待办弹窗测试使用真实离屏
`QQuickWindow`，会验证返回请求能够关闭打开的 Popup。

## 二、为什么仍需人工验收

离屏渲染无法可靠模拟 Windows 125%/150% 缩放、手机刘海、厂商输入法、系统字体放大、
Android 手势导航和真实触摸命中。自动测试也无法判断卡片层级是否舒服、文字是否显得
拥挤。因此 UI-5 不会因为 60 项测试通过就直接宣布完成。

本课重写了 `docs/ACCEPTANCE_CHECKLIST.md`，把验收分为：

- Windows 六种尺寸/缩放场景；
- Android 竖屏、宽屏和 800 × 360 dp 短横屏；
- 返回键、输入法和安全区；
- 记账、课表、天气、待办四个模块的核心流程；
- 可复现的问题记录模板。

清单中的自动项目已经勾选，真实设备项目保持未勾选，避免把“待验收”误写成“已完成”。

## 三、本轮界面检查边界

尝试启动本地 Debug 窗口进行自动截图时，Windows 界面控制环境拒绝读取未登记的 StuKit
窗口。因此本轮只确认应用能正常显示并持续运行，没有伪造或推断实际截图结果。真实
窗口的视觉结论必须由人工按清单检查，或在后续获得可读取窗口的验收环境后补充。

## 四、执行方式

1. 先用 Windows Debug Kit 按清单调整窗口尺寸与系统缩放。
2. 每个尺寸快速遍历首页和四个模块，再完成一次完整业务流程。
3. 用 Android ARM64 Debug Kit 安装现有 APK，重点检查输入法、旋转、返回键和安全区。
4. 通过项改成 `[x]`；失败项按模板记录设备、尺寸、步骤、实际结果和截图。
5. 将问题反馈给我后，按阻塞程度逐项修复并重新运行自动回归。

## 验收结果

- 自动验收基线全部通过。
- 人工验收清单已经细化并可直接执行。
- Windows 视觉验收与 Android 真机验收仍待完成，因此 UI-5 和 M9 保持“验收中”。
