# 第二十七课：SQLite 数据备份与恢复

## 本课定位

第二十六课完成后，记账 MVP 已能创建、管理、查询和筛选数据。下一阶段不急着增加
更多页面，而是先保护用户已经录入的数据。本课将建立本地数据库备份与恢复流程，
并把平台文件选择与数据操作分开，为 Windows 发布和后续 Android 适配打基础。

## 1. 本课目标

- 将正在使用的 SQLite 数据库安全备份到用户选择的位置。
- 恢复前验证候选文件确实是 StuKit 数据库且版本可支持。
- 恢复前自动保留当前数据的安全副本。
- 恢复过程中关闭数据库连接，成功后重新初始化记账模块与页面状态。
- 失败时保留原数据库，并向用户显示可理解的错误。
- QML 只负责选择文件、二次确认和显示结果，不直接复制数据库文件。
- 文件路径能力保持跨平台，不把 Windows 路径规则写进业务层。

## 2. 为什么不能直接复制正在使用的数据库

SQLite 可能正在执行事务，数据库也可能启用辅助日志文件。直接在资源管理器中复制
主文件，不能保证得到一致快照。备份应通过 SQLite 提供的一致性机制生成，恢复则
必须在所有连接释放后进行。

第一版计划使用明确的基础设施服务：

```text
QML FileDialog
  -> DataMaintenanceViewModel
  -> DatabaseBackupService
  -> SQLite / filesystem
```

该服务属于 Infrastructure，因为它依赖数据库连接与文件系统；ViewModel 负责把
结果转换为界面状态，Domain 和记账用例不感知备份文件。

## 3. 备份策略

- 备份开始前确认数据库已完成迁移且连接可用。
- 使用 SQLite 一致性快照能力写入新的目标文件。
- 不覆盖源数据库。
- 目标已存在时要求用户先明确确认。
- 完成后重新打开备份文件，检查关键表和迁移版本。
- 备份文件使用可识别的日期时间名称，但名称不参与数据正确性判断。

## 4. 恢复策略

恢复是高风险操作，按以下顺序执行：

1. 只读验证候选数据库及其迁移版本。
2. 为当前数据库创建自动回退副本。
3. 释放 ViewModel、Repository 和 SQLite 连接。
4. 用已验证文件替换当前数据库。
5. 重新初始化组合根并刷新所有页面状态。
6. 如果替换或初始化失败，恢复自动回退副本。

界面必须说明“恢复会替换当前数据”，并要求二次确认。测试不会只验证成功路径，
也会故意提供损坏文件、普通 SQLite 文件和不支持版本的 StuKit 文件。

## 5. Android 后手

Windows 与 Android 的主要差异是用户如何选择和授权访问文件。数据库验证、快照、
关闭连接和重新初始化流程仍可复用。文件选择结果在边界处转换为本地可操作路径；
如果 Android 返回内容 URI，则由平台适配层先复制到应用临时目录，再交给同一个
备份恢复服务，避免把 Android API 扩散到记账模块。

## 6. 预计文件变化

```text
src/features/accounting/infrastructure/backup/DatabaseBackupService.h/.cpp
src/features/accounting/presentation/DataMaintenanceViewModel.h/.cpp
src/features/accounting/qml/AccountingHomePage.qml
src/app/AccountingModule.h/.cpp
相关单元测试、集成测试与文档
```

具体类名可在实现时根据职责微调。本课预计不修改领域实体，也不新增业务表字段。

## 7. 测试计划

- 备份包含当前三张业务表、迁移记录和实际数据。
- 备份期间源数据库仍可保持一致。
- 无效目标、不可写目录和已有文件得到稳定错误。
- 非 StuKit 数据库、损坏文件和未来版本数据库不能恢复。
- 恢复成功后账户、分类、流水、余额和筛选页面重新加载。
- 恢复失败后原数据仍可使用。
- QML lint、完整自动测试和 Windows 启动检查通过。
