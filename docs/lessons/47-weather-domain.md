# 第四十七课：天气领域模型

## 本课目标

本课开始天气模块，但暂时不联网。先建立一套与 Open-Meteo、Qt Network 和 QML 都解耦
的稳定业务数据，让后续网络响应只有通过校验后才能进入页面。

## 1. `WeatherLocation`

`WeatherLocation` 不是一个随意的字符串。它同时保存显示名称、国家/地区、一级行政区、
IANA 时区和经纬度，并验证：

- 地点名称不能为空且不能过长；
- 纬度必须在 -90～90，经度必须在 -180～180；
- 坐标必须是有限数，拒绝 `NaN` 和无穷值；
- 时区 ID 必须能被 `QTimeZone` 识别。

时区属于地点本身。预报日期、日出和日落必须按目标城市的本地时间解释，不能直接套用
电脑当前时区。

## 2. `WeatherCondition`

网络接口使用 WMO 数字天气代码。页面若到处判断 `code === 61`，会把供应商协议泄漏到
QML，也很难统一文案和图标。本课把代码归一成 `WeatherCondition` 枚举，并集中处理：

- 0～3：晴到阴；
- 45、48：雾；
- 51～57：毛毛雨；
- 61～67：雨；
- 71～77：雪；
- 80～86：阵雨/阵雪；
- 95、96、99：雷暴。

未知或未来新增的代码映射为 `Unknown`，不会造成崩溃。

## 3. `WeatherForecast`

一个预报聚合包含地点、当前天气、逐日天气和 UTC 抓取时间。工厂统一验证：

- 温度、湿度、降水、风速和风向范围；
- 每日最低温不高于最高温；
- 日出早于日落；
- 每日数据按日期升序且日期不重复；
- 天数为 1～16；
- 抓取时间明确使用 UTC。

这里的范围检查不是判断天气是否“正常”，而是阻止明显损坏的 JSON、字段错位或单位
误用继续传播。例如把风速的 m/s 错当成 km/h 时，基础设施层必须先完成单位转换。

## 4. 为什么本课不调用真实 API

领域测试必须快速、稳定、离线可运行。若单元测试依赖公网，会因为网络波动、接口限流、
当前天气变化或供应商维护而随机失败。

本课测试只构造固定数据，覆盖有效地点、坐标和时区边界、WMO 代码映射、预报排序、
重复日期和数值范围。下一课会定义异步 Application 端口，再由后续 Infrastructure
实现 Open-Meteo。

## 5. 验收点

- `WeatherLocation` 会规范化文本并拒绝非法坐标和时区。
- WMO 天气代码只在一个位置转换为稳定枚举。
- `WeatherForecast` 拒绝损坏、乱序和重复的日预报。
- Weather Domain 只依赖 Qt Core，不依赖 Qt Network、QML 或其他业务模块。
- `weather.domain` 单元测试通过。
