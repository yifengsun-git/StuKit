卡片、输入框、下拉框和弹窗，再用这些组件完成记账首页的第一轮信息层级调整。

## 为什么共享组件比逐页修改重要

如果每个页面分别编写颜色、边距、焦点边框和弹窗宽度，后续 Android 适配时需要在
多个文件中重复修复同一问题。共享组件把视觉规则集中到一处：业务页面只表达“这里是
输入框”或“这里是内容卡片”，桌面与移动端的具体尺寸规则由组件和主题负责。

这种拆分不会让 QML 变成业务层。组件仍然只处理显示和交互状态，金额校验、数据保存、
数据库访问等规则继续留在 C++ 的 Domain、Application 和 Presentation 层。

## 本课排查的两个布局问题

### 1. 确认弹窗的绑定循环

两处确认弹窗把可换行 `Label` 的宽度直接绑定到父内容区，而父弹窗的隐式高度又依赖
这个文本的换行结果，形成相互依赖。修复方式是使用 `ColumnLayout` 包裹文本，并通过
`Layout.fillWidth` 由布局系统分配宽度。

### 2. 折叠卡片展开后高度不变

数据工具最初使用 `Flow` 的内容高度直接控制 Layout 高度，这会让位置器和布局系统相互
求值。之后还发现共享卡片只依赖 `ColumnLayout.implicitHeight`，可见子项变化时没有可靠
刷新。最终做法是：

- 工具按钮改用响应式 `GridLayout`，窄屏一列、桌面三列；
- `AppSectionCard` 根据当前可见子项的隐式高度计算自身高度；
- 集成测试同时验证折叠状态、展开状态和卡片高度变化。

这个修复位于共享组件，因此以后其它模块使用可折叠卡片时也能直接受益。
